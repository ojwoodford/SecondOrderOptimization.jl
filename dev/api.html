Primary Functions

SecondOrderOptimization.HessianObjective — Type
HessianObjective(f, fdf!; H = nothing)

An objective given by its cost and by its gradient and Hessian, for optimize and optimize!.

  • f(x) -> cost returns the scalar cost at x.
  • fdf!(g, H, x) -> cost writes the gradient into g and the Hessian into H (both arrive zeroed), and returns the cost at x.
  • H is the Hessian prototype: nothing (a static or dense system sized from x0), a Matrix, an MMatrix, a SparseMatrixCSC, or another package's prototype for which that package implements DampedLinearSolve's linear-system contract (a SchurBlockHessian, for Schur-complement elimination). The type of H selects the linear system, including elimination for a SchurBlockHessian; the linsolver option then names the solver for that system.

The Hessian prototype

  • Fill both triangles. fdf! must write the full symmetric Hessian. Some solvers read only the upper triangle (dense Cholesky and Bunch-Kaufman, sparse :cholesky), but sparse :auto/:ldl need both, and :qr and the predicted cost reduction read every stored entry, so an upper-triangle-only H gives a wrong step or a wrong step-quality estimate.
  • Size and element type. H must be n×n, where n == nvars(x0); a mismatch is a DimensionMismatch. The element type of H, Float64 or Float32, is the linear system's: a Float32 prototype (a Matrix{Float32}, SparseMatrixCSC{Float32}, MMatrix or SchurBlockHessian{Float32}) gives a single-precision Hessian, its reduction and its factorization, while the variables, the gradient g, the step, the damping and the costs stay Float64. fdf! is handed g::Vector{Float64} and H in the prototype's type. A dense prototype of another matrix type is copied into a Matrix of its element type. Any other element type, or a linsolver that does not offer Float32 for that system, is an ArgumentError (DampedLinearSolve's "Precision"). Without a prototype the Hessian is Float64.
  • Missing diagonal entries. A sparse prototype should store every diagonal entry (explicit zeros are fine). If one is missing, a new matrix with explicit zeros on the diagonal is built and handed to fdf! in place of the prototype; its nzval layout differs from the prototype's, so an fdf! that writes by precomputed nzval positions of its own prototype would write to the wrong entries. Writing through H[i, j] works either way.
  • Which matrix holds the final Hessian. fdf! writes into the linear system's own matrix. That is the prototype itself for a Matrix, MMatrix or a sparse matrix with every diagonal entry stored, and a copy otherwise. With a reused workspace, the matrix is the one from the call that built the workspace: an objective whose H is a different object of the same type and size (or, for a sparse H, the same pattern) reuses the cached system, and its H is left untouched.

Example

f(x) = (1 - x[1])^2 + 100 * (x[2] - x[1]^2)^2
function fdf!(g, H, x)
    g[1] = -2 * (1 - x[1]) - 400 * x[1] * (x[2] - x[1]^2)
    g[2] = 200 * (x[2] - x[1]^2)
    H[1, 1] = 2 - 400 * x[2] + 1200 * x[1]^2
    H[1, 2] = H[2, 1] = -400 * x[1]
    H[2, 2] = 200
    return f(x)
end
obj = HessianObjective(f, fdf!)
SecondOrderOptimization.JacobianObjective — Type
JacobianObjective(f, resjac!, J)

A least-squares objective given by its cost and by its residual and Jacobian, for optimize and optimize!. By default the linear systems are solved by a QR factorization of the Jacobian, never by forming JᵀJ, which is more accurate when J is ill conditioned: a dense Householder QR for a dense J, and SuiteSparse's sparse QR (SPQR) for a sparse one. For a dense J, linsolver = :cholesky or :ldl solves the normal equations instead (below).

  • f(x) -> cost returns the true scalar cost at x. Trial points are scored with f: the optimizer never derives the cost from the residual, so the cost need not be ½‖r‖² (with robust weighting it is not).
  • resjac!(r, J, x) -> cost writes the residual into r (length m) and the Jacobian into J (m × nvars(x), the derivative of r along the update dx of update(x, dx)), and returns the cost at x, equal to f(x).
  • resjac! sets r and J; it does not add to them. Unlike g and H for fdf! in HessianObjective, they are not zeroed before each call: the optimizer never writes to r or J. So resjac! must set every entry of r on every call, and every entry of J that it writes at all must be set on every call. Entries of J that resjac! never writes keep the values the caller put in the prototype: a caller whose resjac! writes only part of J supplies a prototype with the rest already set (normally zeros(m, n), for structural zeros). With an integer m the optimizer allocates J itself, as zeros. An entry written at some x and skipped at another keeps its old value, which is a bug in resjac!.
  • J is required: a Matrix or SparseMatrixCSC{T, Int} prototype (m × nvars(x0)), T = Float64 or Float32, or an integer m, the number of residuals, for a dense Float64 system with its own matrix. A Float32 prototype gives a single-precision J and factorization; resjac! is handed r::Vector{Float64} and J in the prototype's type, and the gradient Jᵀr, the step and the costs are Float64. A linsolver that does not offer Float32 for the system (SPQR, for a sparse J) is an ArgumentError. A sparse prototype's stored entries are its pattern: resjac! must write only stored entries (through nonzeros(J), or J[i, j] for a stored (i, j)). Writing any other entry inserts it, which changes the pattern, and the run throws an ArgumentError.
  • J may also be another package's prototype for which that package implements DampedLinearSolve's linear-system contract, such as a SchurBlockJacobian{T, RType} (T Float64 or Float32: the tables in T, the residual Float64, as BlockLinearSystems documents): the variables are partitioned into retained and eliminated blocks, and each step eliminates the eliminated blocks by QR, solves the reduced problem in the retained variables and back-substitutes. resjac! writes the Jacobian blocks and the residuals into J by row block (through that package's blockentry, block(J, k, entry, nrows, ncols) and residual_block(J, k)); its r argument is then an empty vector. RType, Matrix{T} or SparseMatrixCSC{T, Int}, is the storage of the reduced system. A prototype is the matrix resjac! writes into, with its values (a trial system, for callbackchangesstate = false, works on a copy made at the start of the run), except with an OptimizationWorkspace: a workspace owns its Jacobian storage, set from the prototype handed in at the start of each run, and the prototype itself is then never written.

The quadratic model at x is cost + (Jᵀr)ᵀdx + ½‖J dx‖²: the gradient Jᵀr is computed by the optimizer, and there is no residual-only callable. The model's gradient matches the true cost's gradient only when the cost is ½‖r‖² near x; for a reweighted cost, scale r and J so that this holds.

Supported combinations

Every row takes every iterator: the four built-in ones, :levenbergmarquardt, :levenbergmarquardt_dtd, :dogleg and :newton (Gauss-Newton), and any written through the iterator interface (the tutorial's gradient descent uses only the gradient Jᵀr and never solves the linear system). Everything else is rejected with an ArgumentError before f or resjac! is called: any other prototype type, element type or index type, and any other linsolver.

The model Hessian is JᵀJ, so iterator = :newton is Gauss-Newton: each step solves JᵀJ dx = -Jᵀr by the system's solver, with Newton's diagonal shift if the solve reports J numerically rank deficient. :levenbergmarquardt_dtd scales the damping by the running maximum of the squared column norms of J (the diagonal of JᵀJ).

With a sparse J, each solve (each damping value tried) is a numeric SPQR factorization of [J; √λ D^½], whose ordering and symbolic analysis are done once, when the system is built. SPQR allocates its working memory inside each factorization and frees it again; nothing else allocates in the loop. The same holds for :auto and :qr with a SchurBlockJacobian{Float64, SparseMatrixCSC{Float64, Int}} (SPQR is Float64 only): the reduced Jacobian J̃ has a fixed pattern, filled after each elimination, and [J̃; √λ D_r^½] is factored by SPQR in the same way.

linsolver = :lsmr (with using Krylov) solves each damped step iteratively by LSMR on J, dense or sparse, with the damping as LSMR's regularization and the Marquardt scaling as its preconditioner N: nothing is factorized or augmented, JᵀJ is never formed, and nothing allocates. Its tolerances are Krylov's defaults (etol, axtol, btol = √eps, conlim = 1/√eps, at most m + n iterations), starting values that have not been measured. LSMR does not detect a numerically rank-deficient J, except m < n undamped, which is reported as the QR solve reports it.

linsolver = :cholesky or :ldl, with a dense J, solves the normal equations: the upper triangle of JᵀJ is formed from J once per linearization (BLAS syrk, about mn²/2 multiply-adds), and each damping value tried factors JᵀJ + λD (n³/3, independent of m) by Cholesky or Bunch–Kaufman, as for a HessianObjective. That costs less than QR (about 2mn²) when m is well above n, but squares the condition number of J, so it suits a well-conditioned J; :auto stays QR. The product and the factorization are BLAS and LAPACK calls. See DampedLinearSolve's page on solvers for the costs and the damping floor.

For a small problem with a static number of variables (x0 a Number, a StaticVector or a tuple of them, with at most MAX_STATIC_SYSTEM variables) and a dense J with m·n ≤ 48, the optimizer uses a static system: J is an MMatrix and r an MVector, and the QR solves are StaticArrays'. So J may be any AbstractMatrix the optimizer allocates: write it by J[i, j], not by assuming a Matrix. With a Matrix prototype the static system works on a copy, and the prototype itself is not written. The cap is a starting value, measured to be where the static system is faster.

A prototype whose column count is not nvars(x0) is a DimensionMismatch.

Example

t = collect(range(0, 1; length = 20))
y = @. 2.0 * exp(-1.5 * t)
f(x) = 0.5 * sum(abs2, @. x[1] * exp(x[2] * t) - y)
function resjac!(r, J, x)
    @. r = x[1] * exp(x[2] * t) - y
    @. J[:, 1] = exp(x[2] * t)
    @. J[:, 2] = x[1] * t * exp(x[2] * t)
    return 0.5 * sum(abs2, r)
end
x, result = optimize([1.0, 0.0], JacobianObjective(f, resjac!, length(t)))
SecondOrderOptimization.optimize — Function
optimize(x0, obj::HessianObjective, options=OptimizationOptions(); callback=nullcallback, workspace=nothing, startstats=nothing) -> (x, result)
optimize(x0, obj::JacobianObjective, options=OptimizationOptions(); callback=nullcallback, workspace=nothing, startstats=nothing) -> (x, result)

Minimizes the objective obj starting from x0, and returns the best point found and the OptimizationResult. x0 is not modified: the optimization runs on copyvars(x0). Works for any variable type, including immutable ones (Number, StaticVector, custom manifold types); for a mutable x0, optimize! avoids the copy.

Takes the same arguments as optimize!, including either objective type.

Example

using SecondOrderOptimization, StaticArrays

f(x) = (1.0 - x[1])^2 + 100.0 * (x[2] - x[1]^2)^2
function fdf!(g, H, x)
    g[1] = -2.0 * (1.0 - x[1]) - 400.0 * x[1] * (x[2] - x[1]^2)
    g[2] = 200.0 * (x[2] - x[1]^2)
    H[1, 1] = 2.0 - 400.0 * x[2] + 1200.0 * x[1]^2
    H[1, 2] = -400.0 * x[1]
    H[2, 1] = -400.0 * x[1]
    H[2, 2] = 200.0
    return f(x)
end

x0 = @SVector [-1.2, 1.0]
x_opt, res = optimize(x0, HessianObjective(f, fdf!))

# The same problem as two residuals, r = [1 - x₁, 10(x₂ - x₁²)], with cost ½‖r‖²
function resjac!(r, J, x)
    r[1] = 1.0 - x[1]
    r[2] = 10.0 * (x[2] - x[1]^2)
    J[1, 1] = -1.0
    J[2, 1] = -20.0 * x[1]
    J[2, 2] = 10.0
    return 0.5 * (r[1]^2 + r[2]^2)
end
x_opt, res = optimize(x0, JacobianObjective(x -> 0.5 * f(x), resjac!, 2))
SecondOrderOptimization.optimize! — Function
optimize!(x0, obj::HessianObjective, options=OptimizationOptions(); callback=nullcallback, workspace=nothing, startstats=nothing) -> result
optimize!(x0, obj::JacobianObjective, options=OptimizationOptions(); callback=nullcallback, workspace=nothing, startstats=nothing) -> result

Minimizes the objective obj starting from x0, updating x0 in place, and returns the OptimizationResult. On return x0 holds the best point found.

x0 must be a variable that is updated in place (ismutablevar(x0) from OptimizationVariableInterface: e.g. a Vector, an MVector, or a Vector of static blocks). For a Number, an SVector or any other immutable variable it throws an ArgumentError: use optimize, which returns the solution.

Arguments

  • x0: Starting point, overwritten with the solution.
  • obj: The objective. A HessianObjective gives the cost, its gradient and Hessian, and the Hessian prototype. A JacobianObjective gives the cost, the residual and its Jacobian, and the Jacobian prototype or number of residuals; it supports every iterator (:newton is then Gauss-Newton) and the linsolver values its docstring lists for each prototype, and anything else is an ArgumentError before f or resjac! is called.
  • options::OptimizationOptions: Optimization settings and stopping criteria.

Keyword Arguments

  • callback = nullcallback: Callback invoked per iteration: callback(cost, x_trial, data, iteratedata) -> (cost, terminate_flags).
  • workspace = nothing: Optional OptimizationWorkspace for memory reuse.
  • startstats = nothing: Time and allocation counters at the start, for the timings in the result (a Stats); nothing reads them at the call (without statistics, collectstats = false, the clock alone).

Options & Results

SecondOrderOptimization.OptimizationOptions — Type
OptimizationOptions(; kwargs...)

Stores configuration options and stopping criteria for second-order optimization.

Keyword Arguments

  • maxiters::Int = 100: Maximum number of outer iterations (linearization evaluations).
  • reldcost::Float64 = 1e-12: Minimum relative change in cost in one iteration required to continue: the run stops, converged (TERMINATION_REL_DCOST), when an iteration changes the cost by less than reldcost * abs(bestcost), a rise as well as a fall. It is kept tight, since a single iteration with a tiny change is not convergence (a run crawling across a flat valley has many); the slower test is stalltol. Not tested after a step the iterator restricted (a truncated or shifted dogleg step, a shifted Newton solve, an LM step whose damping outweighs the curvature along it), which is small because of the safeguard, not because of convergence.
  • absdcost::Float64 = 1e-15: Minimum absolute change in cost, in either direction, in one iteration required to continue (converged, TERMINATION_ABS_DCOST).
  • dstep::Float64 = 1e-15: Minimum infinity-norm of parameter step vector to continue. Like reldcost, not tested after a restricted step.
  • gtol::Float64 = 0.0: Gradient infinity-norm threshold for termination.
  • maxstall::Int = 3: Maximum number of consecutive iterations in which the best cost does not improve significantly (by more than stalltol relative, counted from the last significant improvement; a rise in cost never improves it). After more than that the run stops: stalled (TERMINATION_STALLED, converged) if the cost has settled: at least one of those iterations left the cost within stalltol (relative) above the cost at the last significant improvement, and none raised it by more than sqrt(stalltol) (relative; the bound is computed from stalltol when the options are created). Otherwise TERMINATION_MAX_FAILS (a failure: the cost kept rising, or jumped).
  • stalltol::Float64 = 1.5e-8: Relative improvement in the best cost that counts as significant for maxstall; about sqrt(eps(Float64)), the change in cost that rounding can produce near a minimum computed with cancellation. With stalltol = 0, maxstall counts consecutive iterations that raise the cost, as it did before stalltol existed. A stalled termination says that progress has become negligible at the best point found. It cannot tell a minimum from a flat valley crossed slowly: whether the step was held back by damping or a trust radius is known only to the iterator. Check the gradient (gtol) when that matters.
  • maxtime::Float64 = 30.0: Maximum wall-clock optimization runtime in seconds.
  • iterator::Symbol = :levenbergmarquardt: Iterator algorithm: one of the four built in (:newton, :levenbergmarquardt, :levenbergmarquardt_dtd, :dogleg), or one defined through IteratorInterface (the manual's tutorial writes a gradient descent, :gradientdescent).
  • linsolver::Symbol = :auto: Linear solver method: :auto, :cholesky, :ldl or :qr; :cg or :minres (Krylov solvers for a Hessian) and :lsmr (for a JacobianObjective only), via Krylov.jl; or :pardiso, via Pardiso.jl. Which of these an objective accepts is set by its prototype: see HessianObjective and the table of supported combinations in JacobianObjective (a dense Jacobian takes :auto, :qr, :cholesky, :ldl and :lsmr; a sparse one :auto, :qr and :lsmr).
  • callbackchangesstate::Union{Bool, StaticBool} = false: Set true if callback modifies problem state.
  • collectstats::Union{Bool, StaticBool} = true: Whether to time the run and count its allocations. With false, no clock is read around an evaluation or a solve and the allocation counters are not read: every time and allocation field of the OptimizationResult is zero (and show says that statistics were not collected), while the counts of iterations, cost and gradient evaluations and linear solves, the costs and the termination are as with true. maxtime is still enforced, by one reading of the clock per iteration. Held as a type parameter, so the choice is made at compile time; a workspace built for one setting is not reused for the other.

Example

opts = OptimizationOptions(
    iterator = :dogleg,
    linsolver = :cholesky,
    maxiters = 50,
    gtol = 1e-6
)
SecondOrderOptimization.OptimizationResult — Type
OptimizationResult

Holds summary statistics and results from an optimization run.

Fields

  • startcost::Float64: Cost prior to optimization.
  • bestcost::Float64: Final minimum cost achieved.
  • timetotal::UInt64: Total optimization time in nanoseconds.
  • timeinit::UInt64: Initialization time in nanoseconds.
  • timecost::UInt64: Time spent evaluating cost function f.
  • timegradient::UInt64: Time spent computing gradients and Hessians fdf!.
  • timesolver::UInt64: Time spent solving linear systems.
  • niterations::Int: Total outer iterations performed.
  • costcomputations::Int: Total cost evaluations performed.
  • gradientcomputations::Int: Total gradient/Hessian evaluations performed.
  • linearsolves::Int: Total linear solves performed.
  • termination::Int: Bitmask indicating termination reasons.
  • iterator::Symbol: The iterator used, as selected by the iterator option (for example :dogleg).
  • initallocations::Int: Heap allocations during setup.
  • initallocated::Int: Bytes allocated during setup.
  • optimizeallocations::Int: Heap allocations during optimization loop.
  • optimizeallocated::Int: Bytes allocated during optimization loop.

Example

x_opt, result = optimize(x0, HessianObjective(f, fdf!))
println("Final cost: ", result.bestcost)
println("Iterations: ", result.niterations)
SecondOrderOptimization.isconverged — Function
isconverged(x::OptimizationResult) -> Bool

Whether the optimization converged: it stopped on at least one convergence criterion, and nothing went wrong that makes the point it returned untrustworthy.

  • Convergence criteria: TERMINATION_REL_DCOST and TERMINATION_ABS_DCOST (an iteration changed the cost, in either direction, by less than reldcost or absdcost), TERMINATION_STEP_SIZE (the step was below dstep), TERMINATION_GRAD_TOL (the gradient was below gtol) and TERMINATION_STALLED (the best cost improved by less than stalltol relative for more than maxstall iterations, at least one of them stayed within that band, and none rose by more than sqrt(stalltol) relative). At least one must be set. A stalled run has stopped making progress at the best point it found; that is not proof of a minimum (see OptimizationOptions).
  • Failures, whatever else is set: anything non-finite (TERMINATION_COST_INF, TERMINATION_COST_NAN, TERMINATION_STEP_INF, TERMINATION_STEP_NAN, TERMINATION_GRAD_INF, TERMINATION_GRAD_NAN, TERMINATION_START_NOT_FINITE), and TERMINATION_LINSOLVER_FAILED. So a small step to a point whose cost is not finite is not converged, nor is a small gradient at a start point whose cost is not finite.
  • Neither: a limit (TERMINATION_MAX_FAILS, TERMINATION_MAX_ITERS, TERMINATION_MAX_TIME). Alone it is not convergence, but with a convergence criterion the run is converged: one that meets a criterion on its last allowed iteration, or whose cost bounces at the minimum until maxstall is reached, has converged.

To ask why a run stopped, test the exported bit masks against result.termination, for example result.termination & TERMINATION_MAX_FAILS != 0. A callback that asked to stop leaves its flags in result.termination >> 16. show(result) prints a message for every bit set.

SecondOrderOptimization.OptimizationWorkspace — Type
OptimizationWorkspace()
OptimizationWorkspace(x0, obj::HessianObjective, options=OptimizationOptions(); startstats=Stats())
OptimizationWorkspace(x0, obj::JacobianObjective, options=OptimizationOptions(); startstats=Stats())

Preallocated cache for linear systems, solver factorizations, and trial variable buffers, enabling zero-allocation repeated optimizations.

The cache is reused when the variable type, dimension and block layout, the options type and the objective's structure all match: for a HessianObjective the Hessian's type and structure, for a JacobianObjective the number of residuals m. A workspace built for one objective kind is never reused for the other. Otherwise it is rebuilt (and, for a workspace whose type parameters can't hold the new data, emptied, with a one-time warning). A reused workspace keeps the Hessian matrix of the call that built it: see The Hessian prototype in HessianObjective. A workspace for a JacobianObjective instead owns its Jacobian storage (a copy of the prototype, or zeros for an integer m), so a prototype matrix is never written when a workspace is used, and a different prototype matrix of the same size does not rebuild the workspace: at the start of each run, every cached Jacobian (the trial system's too) is set to the contents of the prototype handed in (or to zeros, for an integer m), so the run starts exactly as a fresh one would. resjac! then writes into the workspace's storage.

Example

obj = HessianObjective(f, fdf!)
ws = OptimizationWorkspace(x0, obj, options)
for trial in 1:10
    x_opt, res = optimize(x0, obj, options; workspace=ws)
end

Every run times its evaluations and solves and counts its allocations, into the time and allocation fields of the result. For a small problem solved many times, where reading the clock is a visible part of the cost of a run, pass collectstats = false to OptimizationOptions: those fields are then zero, and everything else in the result is as before.

Why a run stopped is in result.termination, a bitfield. Test it against the exported masks, for example result.termination & TERMINATION_GRAD_TOL != 0, and use isconverged for whether the run converged:

Bit mask of OptimizationResult.termination, set when an iteration changed the cost, up or down, by less than reldcost relative to the best cost, after a step the iterator did not restrict (see reldcost in OptimizationOptions). Bit mask of OptimizationResult.termination, set when an iteration changed the cost, up or down, by less than absdcost. A convergence criterion. Test it with result.termination & TERMINATION_ABS_DCOST != 0; see isconverged.

Bit mask of OptimizationResult.termination, set when the step was below dstep (infinity norm) and the iterator did not restrict it (see reldcost in OptimizationOptions). A convergence criterion. Test it with result.termination & TERMINATION_STEP_SIZE != 0; see isconverged.

Iterators and Linear Solvers

An iterator is chosen by the iterator keyword of OptimizationOptions, as a symbol: one of the four built in, :newton, :levenbergmarquardt, :levenbergmarquardt_dtd or :dogleg, or one you define (gradient descent is the example of Writing Your Own Iterator), through the interface described in The Iterator Interface. A linear solver is chosen by the linsolver keyword, also as a symbol: :auto, :cholesky, :ldl or :qr, and those the extensions below add.

The linear systems and their solvers are those of DampedLinearSolve.jl, on which this package is built: its documentation states the linear-system contract the iterators use, the solvers each system takes and how :auto chooses, and how to implement the contract for your own storage. OptimizationOptions validates linsolver by asking it.

SecondOrderOptimization.IteratorInterface — Module
SecondOrderOptimization.IteratorInterface

The interface for writing an iterator: the methods an iterator defines (iteratorname, construct, reset!, iterate!, and optionally restrictedstep, triallinearization and linearize!), and the functions it calls on the loop's state data; and check_iterator, which checks an iterator against the contract. See the manual's page on the iterator interface.

Extension Solvers

Loading these packages adds solvers, through DampedLinearSolve's package extensions:

  • Krylov.jl: Provides iterative Krylov subspace linear solvers. :cg is the Krylov solver for a Hessian.
    • :cg: Conjugate Gradients for symmetric positive-definite systems. Reports the system as indefinite on nonpositive curvature.
    • :minres: MINRES for symmetric indefinite systems.
    • On sparse systems, :cg and :minres are Jacobi (diagonal) preconditioned whenever the damped diagonal is positive.
    • :lsmr: LSMR on the Jacobian of a JacobianObjective (dense or sparse), with the damping as its regularization parameter. Rejected for a HessianObjective, where it would square the condition number of the normal equations again.
    To enable: using Krylov.
  • Pardiso.jl: Provides multithreaded direct sparse factorization using Intel MKL PARDISO or Panua Pardiso.
    • :pardiso: Multi-threaded sparse direct solver for large sparse matrices. The symbolic analysis runs once, when the linear system is built; each solve runs only the positive-definite numerical factorization, and reports the system as not positive definite when it fails.
    To enable: using Pardiso.
  • BlockLinearSystems.jl (which implements DampedLinearSolve's linear-system contract for its own systems): Schur-complement elimination for a SchurBlockHessian prototype. The type of H selects the linear system, including elimination for a SchurBlockHessian: there is no solver symbol or option for it. linsolver then names the solver for the reduced system: :auto or :cholesky (Cholesky, falling back to Bunch-Kaufman) or :ldl (Bunch-Kaufman); any other is an ArgumentError when the system is built. On the Jacobian path, a SchurBlockJacobian{Float64, RType} prototype for a JacobianObjective selects QR elimination of the eliminated blocks; RType (dense Matrix{Float64} or SparseMatrixCSC{Float64, Int}) is the storage of the reduced system, and linsolver names its solver (see the JacobianObjective docstring). With Krylov.jl also loaded (BlockLinearSystems' DampedLinearSolveKrylovExt), :lsmr solves the reduced problem by LSMR on the reduced Jacobian. The elimination kernels run threaded over the structure's chunks only when Polyester.jl is also loaded (BlockLinearSystems' PolyesterExt); otherwise they run serially. A warm run allocates nothing, except that on Julia 1.10 each threaded kernel call may allocate a little (up to 2 048 bytes per thread). To enable: using BlockLinearSystems.
